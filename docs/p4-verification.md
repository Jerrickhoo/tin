# P4 verification — 2026-10-21 (Asia/Manila)

P4.1 and P4.2 are implemented. D9's recommended defaults were adopted under the user's instruction to do P4. P5–P8 remain outside this change. This document records implementation verification; the production follow-up is recorded in [P4 release](p4-release-2026-10-22.md).

## Behavior

- Goals live one level below an envelope. They have a target, one-time/ongoing mode, optional deadline, progress, reserved amount, funding/release actions and an explicit actual purchase. Hold pauses new funding while preserving reservations. Close/archive explicitly releases all remaining current/future reservations, retains history and is terminal.
- The envelope total remains actual signed money. The shared availability function subtracts future budget holds and current goal reservations once. Future goal allocations remain inside their future income hold, so they are not subtracted twice. Home, goal details, budget details and the daily recommendation use this same calculation. Actual overspending is still recordable and shows a funding shortfall.
- New income is split across parent envelopes first. Child percentages then use integer-centavo largest-remainder arithmetic, stable share order and an explicit unreserved remainder. Existing money is not split retroactively. One-time goals cap new funding at their target; overflow stays free. Held/closed goals receive no new automatic funding.
- Each eligible receipt captures the current split revision and rounded funded amounts atomically with its cash entry and optional budget assignment. Future assignments keep that revision at rollover. An unconsumed future capture can be explicitly reviewed under the current split. A source correction can reduce its cash-backed reservation; increasing a corrected receipt does not silently increase the original executed allocation. Voiding/restoring a receipt or goal purchase updates the linked projection. Refunds do not automatically rebuild consumed reservations.
- Fixed and percentage monthly rules produce reviewable occurrences. Percentage requests use actual new parent income assigned to the selected month. Due days 29–31 clamp to month end. A UUIDv5 rule/month identity and unique logical key prevent duplicate execution; a reviewed retry can only increase the funded amount of the existing occurrence. Rule edits apply to new occurrences; an existing occurrence retains its original request and rule version. Pausing affects new funding, not money already reserved. Past months are reviewable individually, with no background catch-up spending.

## Persistence and server checks

Goal events are immutable `ledger_audit.details.goals` records in the existing atomic financial operation. They share owner isolation, local transactions, journal/outbox retry, sync conflict rollback and account reset. No second cash ledger or mutable stored balance is introduced. The goal key is the reservation identity for later P5 integration.

Local and server validation check revision links, event identities, parent/goal ownership, strict fields and integer bounds, source/purchase references, rule snapshots, caps and available free money. The server serializes commands under the existing owner lock, recomputes funding rather than trusting a client amount, and rejects stale previews and competing oversubscription. A failed operation cannot commit partial cash or reservations. Unrelated pending actual expenses survive rejection of a reservation. Pulled cash, goal history and the sync cursor commit together; a malformed goal reference preserves the previous complete snapshot.

JSON export version **4** retains the full goal history. Versions 1–3 remain readable, and a version downgrade containing goals is rejected. Restore remaps envelope IDs and dependent split/capture keys together, preserves goal/rule/event/purchase identities, and validates all links before writing. Both Home and Settings use the complete atomic backup snapshot.

Migration **009** introduces the private validation/projection helpers and wraps the owner-locked financial command. Older clients and direct legacy writes cannot bypass reservations once an account uses goals. Migration **010** is an explicit follow-up to the already rehearsed/applied staging migration: bounded device clock skew is accepted, queued earlier-month reservations are checked against current free funds, and earlier purchases do not block revision of a still-future capture. No previously applied migration was rewritten.

## Reproduce and release

Run `npm run check`, `npm run build`, and the existing disposable SQL rehearsal (`node scripts/check-financial-sql.mjs <pglite/dist/index.js>`). On Windows PowerShell use `npm.cmd` if script execution policy blocks `npm.ps1`.

The existing explicitly disposable staging configuration is reused by `node scripts/probe-p4-staging.mjs migrate` and `node scripts/probe-p4-staging.mjs verify`. Migration mode refuses to reapply installed P4 history. `node scripts/serve-p4-staging.mjs` serves the actual staging build at port 5194. Private sessions/configuration stay in ignored `.local` files.
